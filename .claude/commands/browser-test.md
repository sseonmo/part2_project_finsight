`docs/BROWSER_TEST_CASES.md` 의 브라우저 시나리오를 실행한다.

대상: **$ARGUMENTS**

인자가 비어 있으면 문서에서 아직 `◻︎` 인 시나리오 목록을 먼저 보여주고,
무엇을 돌릴지 사용자에게 물어라. 임의로 전부 돌리지 마라 — 42건은 한 세션에 안 끝난다.

## 1. 환경 준비

```bash
scripts/browser-test/up.sh
```

여러 번 실행해도 안전하다. 쿠키는 20~30분이면 끊기므로 **중간에 인증이 깨지면 다시 돌려라.**

`.env.local` 이 없으면 up.sh 가 막는다. 이대로 진행하면 프로덕션 Supabase 를 때린다 —
`docs/BROWSER_TESTING.md` 의 `.env.local` 절을 먼저 따르게 하라.

## 2. 실행 틀 (매 Bash 호출마다 다시 정의한다)

**셸 함수는 Bash 호출 사이에 유지되지 않는다.** 스크립트를 실행하는 모든 Bash 호출의
맨 앞에 이 두 줄을 붙여라. 빠뜨리면 `run: command not found` 로 죽는다.

```bash
run() { { cat scripts/browser-test/prelude.js; cat; } | dev-browser --browser finsight; }
psql() { docker exec supabase_db_part2_project_finsight psql -U postgres -d postgres "$@"; }
```

- 히어독은 `<<'EOF'` 를 쓴다. 스크립트 안의 `$` 와 백틱이 셸에 먹히면 안 된다.
  셸 변수를 치환해야 할 때만 `<<EOF`.
- **업로드는 한 스크립트에 한 건씩.** dev-browser 스크립트에 30초 제한이 있어
  한 스크립트에서 두 건 이상 올리면 두 번째부터 터진다. 여러 건은 셸 루프로 돈다.

## 3. 시나리오 실행

각 시나리오마다:

1. `docs/BROWSER_TEST_CASES.md` 에서 **해당 절만** 읽는다(문서 전체를 읽지 마라 — 길다).
2. 그 절의 "준비"에 적힌 액터·데이터 상태를 맞춘다
   (`scripts/browser-test/actor.sh` · `scripts/browser-test/reset.sh data`).
3. 절에 적힌 순서대로 `run` / `psql` 을 실행한다.
4. 절의 **기대**와 실제 출력을 대조한다.

판정 규약은 `docs/BROWSER_TESTING.md` 의 "판정 규약" 절을 따른다.
특히 **분류 결과(카테고리)로 성공을 판정하지 마라** — LLM 출력이라 재현되지 않는다.

## 4. 결과 표시

| 표시 | 뜻 |
|---|---|
| ✅ | 이 문서의 절차와 픽스처로 실행해 확인했다 |
| ◻︎ | 아직 이 조합으로 안 돌렸다 |
| ⚠︎ | `docs/KNOWN_ISSUES.md` 의 결함에 걸린다 — **그 방식으로 실패하는 것이 정상이다** |
| 🔍 | 화면으로 판정할 수 없어 DB 확인이 필수다 |

- 기대대로 나왔으면 그 절의 제목 표시를 `◻︎` → `✅` 로 바꾼다.
- 어긋났으면 **문서를 고치지 말고** 실제 출력을 그대로 보고하라.
  `⚠︎` 로 표시된 기존 결함에 걸린 것인지, 새 결함인지 구분해서 말하라.
- 새 결함이면 `docs/KNOWN_ISSUES.md` 에 실측 근거(명령과 출력)와 함께 추가할지 물어라.
  **추정으로 적지 마라.**

## 🚨 하지 말 것

- `.env.local` 을 지우거나 프로덕션 자격증명으로 돌리지 마라.
- 통과하지 않은 시나리오를 `✅` 로 바꾸지 마라. 안 돌린 것은 `◻︎` 로 둔다.
- 로컬 DB 를 통째로 비우기 전에 확인하라 — 기본 시리즈를 다시 올리는 데 시간이 든다.
