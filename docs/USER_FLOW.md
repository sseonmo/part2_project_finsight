# 유저 플로우

이 문서는 화면 전이와 상태 전이의 단일 출처다. UI를 만들 때 여기 적힌 상태·문구·차단 규칙을 그대로 따른다.

## 사용자 유형

| 코드 | 상태 | 특징 |
|------|------|------|
| U1 | 비로그인 방문자 | 랜딩만 본다 |
| U2 | 신규 가입자 (체험 중, 거래 0건) | **아직 CSV를 어디서 받는지 모른다** — 이탈이 가장 많이 나는 지점 |
| U3 | 활성 사용자 (체험 중, 데이터 있음) | 대시보드를 보고 분류를 고친다 |
| U4 | 체험 만료자 (미결제) | 열람은 되고 신규 업로드는 막힌다 |
| U5 | 구독자 | 제한 없음 |
| U6 | 해지자 (결제 기간 잔여) | 기간이 끝날 때까지 구독자와 동일 |
| U7 | 복귀자 (오래 비운 사용자) | 마지막 업로드 이후 몇 달이 비어 있다 |

## 화면

| 라우트 | 화면 | 접근 |
|--------|------|------|
| `/` | 랜딩 | 비로그인. 로그인 상태면 `/dashboard` 로 보낸다 |
| `/auth/callback` | OAuth 콜백 | 처리 후 원래 가려던 경로 또는 `/dashboard` |
| `/dashboard` | 월별 지출 대시보드 | 로그인 필수 |
| `/dashboard/uploads` | 업로드 이력 · 파일 삭제 | 로그인 필수 |
| `/dashboard/uploads/[id]/mapping` | 컬럼 수동 매핑 | job이 `needs_mapping` 일 때만 |
| `/dashboard/subscriptions` | 반복 지출 목록 (구독·정기결제) | 로그인 필수. **`expired` 에서도 열린다** |
| `/dashboard/report/[yearMonth]` | 월간 리포트 | 로그인 필수 |
| `/settings` | 계정 · 구독 · 계정 삭제 | 로그인 필수 |

업로드는 별도 라우트가 아니라 `/dashboard` 안의 다이얼로그로 연다. 첫 업로드까지의 클릭 수를 늘리지 않는다.

**업로드 다이얼로그는 카드를 함께 받는다.** `card_label` 은 `dedupe_key` 의 구성 요소라 비울 수 없다(ARCHITECTURE "중복 방지"). 다만 마찰을 만들지 않는다 — **첫 업로드에는 "카드 1"이 이미 채워져 있고**, 이름은 그 자리에서 고칠 수 있다. 두 번째부터는 기존 카드 목록(`SELECT DISTINCT card_label`) 드롭다운 + "새 카드 추가"다. 카드가 한 장인 사용자는 이 항목을 의식하지 않고 지나간다.

## 상태 머신 1 — `upload_jobs.status`

```
pending ──파일 업로드 완료──> parsing ──거래 저장 완료──> categorizing ──> completed
                                │  ▲
              행이 안 읽힘      │  │ 사용자가 매핑 지정
                                ▼  │
                          needs_mapping

  parsing ──값이 말이 안 됨(sanity check)──> failed
  parsing / categorizing ──복구 불가──> failed
```

| 상태 | 의미 | 사용자가 보는 것 |
|------|------|------------------|
| `pending` | job row는 있고 파일은 아직 Storage에 없음 | "업로드 중" |
| `parsing` | 인코딩 감지 → 컬럼 매핑 → 행 파싱 | "거래 내역을 읽는 중" + 진행률 |
| `needs_mapping` | **행이 안 읽힌다** — 20행 샘플 성공률 90% 미만, 또는 전 행 파싱 실패율 20% 초과 | "어떤 컬럼이 날짜·금액·가맹점인지 알려주세요" + 미리보기 |
| `categorizing` | 거래 저장 완료, 분류 → 신호 탐지 진행 | "카테고리를 분류하는 중" + 진행률 |
| `completed` | 종료 | 결과 요약 (아래 "완료 요약 규칙") + 인사이트 카드 상위 3개 (S28) |
| `failed` | **행은 읽혔는데 값이 말이 안 된다**(sanity check 3종), 또는 복구 불가 | 사유 + 다시 시도 버튼 |

**행이 안 읽히는 것은 언제나 매핑 문제로 취급한다** (ADR-001). 20행 샘플에서 걸리든 전 행에서 걸리든 원인이 같으므로 둘 다 `needs_mapping` 으로 보낸다. "500건 중 500건을 읽지 못했습니다"에 `failed` 를 붙이면 사용자에게 남는 선택지가 없는데, 실제로는 컬럼을 다시 고르면 되는 경우가 대부분이다.

**`failed` 는 컬럼을 다시 골라도 소용없는 경우만이다.** 거래일이 전부 미래거나, 금액을 읽을 수 없거나, 유효 거래가 0건인 파일이다. 데이터 행이 애초에 0건인 파일(헤더만 있는 CSV)은 "거래가 없는 파일입니다"로 안내한다 — 읽지 못한 것이 아니라 읽을 것이 없었기 때문이다.

**완료 요약 규칙** — `completed` 는 항상 네 숫자를 보고한다.
- 새로 추가된 거래 N건
- 중복이라 건너뛴 거래 N건 (`dedupe_key` 충돌)
- 읽지 못한 행 N건 (`skipped_rows`)
- 분류하지 못해 "기타"로 넣은 가맹점 N개

숫자가 0인 항목은 표시하지 않는다. 단 **"새로 추가된 거래 0건"은 반드시 표시한다** — 사용자가 가장 혼란스러워하는 경우다.

네 숫자 외에 **카드 오지정 경고**가 붙을 수 있다(S24b). 숫자가 아니라 문장이고, 조건이 걸릴 때만 나온다.

## 상태 머신 2 — `profiles.subscription_status`

```
저장되는 상태 (subscription_status — 결제 사실만)

  (가입) ──> trialing ──결제 완료──> active ──해지──> canceled
                 ▲                      ▲                 │
                 │                      └─── 재결제 ──────┘
                 └── 최초 1회만

계산되는 권한 (entitlement.ts — 매 요청)

  trialing  + trial_started_at + 7일 > now   → 이용 가능
  trialing  + 7일 지남                        → expired (차단)
  active                                      → 이용 가능
  canceled  + current_period_end > now        → 이용 가능 (active 와 동일)
  canceled  + 기간 지남                        → expired (차단)
```

`canceled` 는 **즉시 차단이 아니다.** Polar의 `current_period_end` 까지는 `active` 와 동일한 권한을 준다.

**`expired` 는 저장된 상태가 아니라 계산 결과다.** `subscription_status` 컬럼은 결제 사실(`trialing`/`active`/`canceled`)만 담고, 만료 여부는 `entitlement.ts` 가 `trial_started_at + 7일` 과 `current_period_end` 를 매 요청 계산해 판정한다. 크론으로 컬럼을 내리는 방식은 실행 지연만큼 공짜 이용 구간이 생기고, 크론이 죽으면 전원이 무제한이 된다. 아래 매트릭스의 `expired` 행은 "계산상 만료된 상태"를 뜻한다.

**코드에서 `status === 'active'` 로 비교하지 않는다.** 상태 문자열과 실제 권한이 어긋나는 지점이 둘(`canceled` 기간 내, `trialing` 만료 후)이라, 직접 비교하는 순간 결제한 사용자가 차단되거나 만료자가 통과한다.

### 권한 매트릭스

| 상태 | 대시보드 열람 | 신규 업로드 | 리포트 생성 | 분류 수정 | 기존 리포트 열람 | 반복 지출 목록 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| `trialing` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `active` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `canceled` (기간 내) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `expired` | ✓ | ✗ | ✗ | ✗ | ✓ | ✓ |

**`expired` 에서 막는 것은 쓰기 전부, 여는 것은 읽기 전부다** (ADR-005). 자기 금융 데이터를 인질로 잡는 제품은 결제가 아니라 탈퇴를 부른다. 분류 수정은 비용이 들지 않지만 쓰기이므로 막는다 — 경계를 "비용이 드는가"로 잡으면 동작마다 판단이 갈려 게이트를 빠뜨린다.

**반복 지출 목록은 LLM을 쓰지 않으므로 `expired` 에서도 열어둔다.** 비용이 들지 않는 기능을 막을 이유가 없고, 오히려 재결제 동기가 된다. 인사이트 카드와 코칭 문단은 각각 업로드·리포트 생성에 종속되므로 위 차단 규칙이 그대로 적용된다.

판정은 전부 `src/lib/entitlement.ts` 에서 하고, Route Handler와 Inngest 함수 양쪽이 이 함수를 호출한다.

| S17 | EUC-KR/CP949 인코딩 | 감지 후 UTF-8 변환 | 사용자에게 노출하지 않는다 (조용히 처리) |
| S18 | 체험 만료 상태로 업로드 시도 | `entitlement` 에서 차단 | 업로드 버튼 자리에 결제 안내. 기존 데이터는 그대로 보인다 |
| S19 | 체크아웃 중 이탈 | 아무 일도 일어나지 않음 | 만료 상태 유지 |
| S20 | 결제했는데 웹훅 지연 | 복귀 페이지에서 최대 30초 폴링 | "결제를 확인하는 중" → 초과 시 "곧 반영됩니다. 새로고침해 주세요" |
| S21 | 데이터가 한 달치뿐 | 전월 대비 계산 불가 | 증감 자리를 비우고 "비교할 지난달 데이터가 없습니다" |
| S22 | 거래가 없는 달 선택 | 빈 상태 | "이 달에는 거래가 없습니다" + 업로드 버튼 |
| S23 | 리포트 생성 후 그 달 거래 추가 | 리포트를 자동으로 다시 만들지 않는다 | 생성 시각("3월 12일에 생성됨")과 "다시 만들기"가 항상 보인다 |
| S24 | 같은 달에 여러 카드 명세서 | 정상 누적. **카드마다 다른 `card_label` 로 올리면** 같은 날·같은 금액·같은 가맹점이 카드별로 1건씩 있어도 둘 다 보존된다 (`card_label` 이 `dedupe_key` 에 포함) | 업로드 이력에 파일별로 카드와 함께 표시 |
| S24b | 두 번째 카드를 첫 카드 이름 그대로 올림 | 거래는 저장하되 카드 오지정 경고를 완료 요약에 함께 띄운다. 같은 `card_label` 의 기존 파일과 `header_hash` 가 다른 것이 근거다 | "이 파일은 '카드 1'로 올린 이전 파일과 형식이 다릅니다. 다른 카드라면 삭제 후 카드를 바꿔 올려주세요" |
| S25 | 업로드 여러 건 동시 진행 | job별 독립 처리 | 진행률 카드를 여러 개 쌓아 보여준다 |
| S26 | 비로그인 상태로 딥링크 | 로그인 후 **원래 가려던 경로로** 복귀 | 무조건 `/dashboard` 로 보내지 않는다 |
| S27 | 계정 삭제 | Storage 객체 + 전 테이블 row 즉시 삭제 | 되돌릴 수 없음을 명시하고 재확인 |

### AI 리뷰 흐름

| # | 상황 | 시스템 동작 | 사용자가 보는 것 |
|---|------|------------|------------------|
| S28 | 업로드 완료 후 인사이트 | CSV에 든 모든 달에 신호를 만들되, 카드는 **가장 최근 달**의 영향도 상위 3개만. 영향도가 없는 `recurring_payment` 은 카드에 올리지 않는다 | 완료 요약 아래 카드 3장. 각 카드는 SQL이 계산한 금액 + LLM 한 문장. "카페·간식이 지난달보다 62,000원(+58%) 늘었습니다" |
| S29 | 첫 달이라 비교 대상이 없음 | 5종 중 `outlier_transaction` 만 작동 | 빈 카드 대신 "다음 달이면 지난달과 비교해 드릴 수 있습니다". 없는 것을 있는 척하지 않는다 |
| S30 | 반복 지출 확인 | `/dashboard/subscriptions` 에서 `recurring_*` 을 SQL로만 조회. 가맹점별로 **가장 최근 `period` row 하나만** 읽는다 | 가맹점 · 금액 · 주기 · 지속 개월 표. `expired` 여도 열린다 |
| S31 | 인사이트가 틀림 | `spending_signals.dismissed_at` 기록 | 카드의 "숨기기". 왜 틀렸는지는 묻지 않는다 (MVP에서 재학습하지 않으므로 물어보면 기대만 만든다) |
| S32 | 구독료 인상 발견 | `recurring_price_up` 이 인상분 × 12로 정렬돼 상위로 올라옴 | "○○ 구독료가 9,900원에서 12,900원으로 올랐습니다. 이대로면 1년에 36,000원을 더 내게 됩니다" |
| S33 | 같은 달을 다시 업로드 | 기존 신호는 두고 새로 발생한 것만 추가 (유니크로 중복 방지) | 새 신호만 카드에 더해진다. 숨겼던 카드는 다시 나타나지 않는다 |
| S34 | 날짜 형식이 모호한 CSV | 전체 행을 스캔해 판별하고, 끝까지 구분되지 않으면 `YYYY-MM-DD` 계열로 가정 | 업로드 이력에 해석한 날짜 형식을 표시한다("03/04/2026 → 3월 4일로 읽음"). 틀렸으면 **그 업로드를 삭제하고 다시 올린다** — 완료된 job의 매핑을 고치는 경로는 MVP에 없다 (ADR-001) |

인사이트 카드의 모든 금액은 `spending_signals.payload` 의 집계값을 그대로 렌더한다. LLM 문장 안의 숫자를 파싱해 표시하지 않는다.

## 검증된 마찰점과 대응

**첫 업로드 앞의 벽이 가장 크다.** U2는 "CSV를 어디서 받는가"를 모른다. 업로드 다이얼로그 안에 주요 카드사·은행별로 내역 다운로드 경로를 한 줄씩 적어둔다. 이 안내가 없으면 가입은 되고 업로드는 안 되는 사용자가 쌓인다.

**대기 시간은 숨기지 말고 설명한다.** 처리에 수십 초가 걸린다. 진행률만 돌리지 말고 지금 무엇을 하는 중인지("거래 내역을 읽는 중" → "카테고리를 분류하는 중")를 함께 보여준다.

**분류 수정은 가맹점 단위로 전파한다.** 거래 한 건씩 고치게 하면 사용자가 같은 작업을 수십 번 반복한다. S4 참조.

**체험 만료는 예고한다.** 만료 2일 전부터 대시보드 상단에 배너를 띄운다. 예고 없이 막히면 사용자는 고장으로 받아들인다.

**첫 달 사용자에게 리포트를 과대 약속하지 않는다.** 비교할 지난달이 없으면 리포트의 가치가 절반이다. S21처럼 없는 것은 없다고 말한다.

**조용히 틀리는 것을 보이게 만든다.** `03/04/2026` 같은 날짜는 3월 4일과 4월 3일 둘 다로 읽히고, 파싱은 어느 쪽이든 성공한다. 시스템이 틀리게 읽어도 화면에는 그럴듯한 숫자가 뜬다. 그래서 해석한 날짜 형식을 업로드 이력에 적어둔다(S34). 사용자가 이상을 눈치챌 수 있어야 하고, 눈치챈 뒤의 복구 경로는 **그 업로드를 삭제하고 다시 올리는 것**이다 — 완료된 job의 매핑을 고치는 UI는 MVP에 만들지 않는다.
