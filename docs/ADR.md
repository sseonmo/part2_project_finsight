# Architecture Decision Records

## 철학
학습 프로젝트지만 실제로 배포하고 지인이 쓴다. 따라서 **작동하는 최소 구현**을 고르되,
틀린 숫자를 보여주거나 남의 데이터가 새는 경로만은 최소 구현을 허용하지 않는다.

---

### ADR-001: 매핑 실패는 묻고, 데이터 이상은 거절한다
**결정**: 컬럼 매핑은 LLM이 자동 추론하고 정상 경로에서는 사용자에게 묻지 않는다. 다만 실패를 둘로 나눈다 — **행이 안 읽히면**(20행 샘플 성공률 90% 미만 또는 전 행 실패율 20% 초과) `needs_mapping` 으로 멈추고 컬럼을 직접 고르게 하고, **행은 읽혔는데 값이 말이 안 되면**(sanity check 3종) `failed` 로 끝낸다. 두 경우 모두 fingerprint를 저장하지 않으며, 수동 확정한 매핑도 sanity check를 통과한 뒤에만 저장한다.
**이유**: 한국 카드사 CSV는 헤더명·날짜포맷·인코딩이 제각각이라 하드코딩이 불가능하고, 정상 경로에 확인 화면을 두면 첫 업로드 이탈이 생긴다. 그래서 자동 추론이 기본이다. 그러나 실패를 전부 거절로 처리하면 LLM이 못 읽는 형식을 가진 사용자에게 **탈출구가 아예 없다** — 몇 번을 다시 올려도 같은 실패를 반복한다. 수동 매핑 화면은 성공률 90% 미만일 때만 뜨므로 정상 경로를 건드리지 않으면서 그 막다른 길을 없앤다. 둘을 나눈 이유는 **묻는 것이 의미 있는 실패와 그렇지 않은 실패가 다르기 때문**이다 — 거래일이 전부 2035년으로 읽히는 파일은 컬럼을 다시 골라도 달라지지 않는다.
**트레이드오프**: 화면 1개(컬럼 선택), 상태 1개(`needs_mapping`), 이벤트 1개(`csv.mapping_confirmed`)가 늘고 워커가 중간 스텝부터 재개할 수 있어야 한다. 그리고 **검사를 통과하는 오답**(승인일↔이용일 혼동)은 두 검사 어느 쪽에도 걸리지 않는다. 사용자가 대시보드를 보고 알아채야 하며, 복구 경로는 업로드 삭제 후 재업로드다. 수동 매핑이 반복 실패할 수 있어 시도 횟수에 상한을 둔다.

### ADR-002: fingerprint 캐시는 개인 범위다
**결정**: `csv_format_fingerprints`의 키는 `(user_id, 헤더 해시)`다. 컬럼 매핑을 전역으로 공유하지 않는다.
**이유**: 전역 공유였다면 한 사람의 오답이 같은 카드사 CSV를 올리는 모든 사용자의 거래를 엉뚱한 달로 보낸다. 개인 캐시만으로도 "같은 사람이 매달 같은 형식을 올린다"는 주 패턴에서 LLM 호출이 사라진다.
**트레이드오프**: 사용자마다 첫 업로드는 반드시 LLM을 한 번 호출한다. 전역 캐시였다면 아꼈을 비용이다.

### ADR-003: dedupe_key에 파일 내 행 순번 대신 조합별 발생 순서를 쓰고, 카드를 키에 넣는다
**결정**: `occurrence`를 "같은 (날짜, 금액, 가맹점) 조합이 그 파일에서 몇 번째로 등장했는지"로 정의한다. 그리고 **`card_label` 을 `dedupe_key` 에 포함한다** — 업로드 시 사용자가 카드를 고르고, 그 값이 키의 구성 요소가 된다.
**이유**: 행 순번을 쓰면 3월치 파일과 3~4월치 파일에서 같은 거래의 순번이 달라져 중복 삽입된다. 조합별 순서는 파일이 달라도 값이 같아 겹치는 기간을 자동으로 막는다. 동시에 같은 날 같은 가게 같은 금액의 **진짜 2건**도 보존한다.
**`card_label` 을 넣는 이유는 그 보존이 파일 하나 안에서만 성립하기 때문이다.** `occurrence` 는 파일 안에서만 세므로, 카드 A와 카드 B의 3월 명세서에 같은 조합이 1건씩 있으면 양쪽 다 `occurrence = 0` 이 되어 키가 같아진다. 두 번째 파일의 진짜 거래가 `ON CONFLICT DO NOTHING` 으로 버려지고, 사용자 화면에는 "중복이라 건너뛴 거래"로 보고된다 — **진짜 2건이 1건으로 줄어드는데 사용자는 중복이 제거된 줄 안다.** `merchant_normalized` 가 지점 코드를 지우므로 강남점·종로점도 같은 이름이 되어 충돌 확률이 더 오른다. PRD가 대상 사용자를 "카드 1~4장"으로 정의한 이상 이것은 예외가 아니라 정상 경로이고, 이 제품이 가장 피하려는 **조용히 틀리기**에 정확히 해당한다.
**트레이드오프**: 파일 전체를 읽어 조합을 세어야 하므로 스트리밍 파싱을 포기하고 메모리에 올린다. sanity check의 비율 판정도 어차피 전체를 요구하므로 같은 대가를 두 번 치르지는 않는다. 개인 카드 명세서 규모(월 수백 행)에서는 문제가 되지 않는다.
`card_label` 쪽 대가는 **업로드 다이얼로그에 항목 하나가 늘고, 사용자가 카드를 잘못 지정하면 방어가 무력해진다**는 것이다. 앞은 첫 업로드에 "카드 1"을 기본값으로 채워 흡수하고(카드 한 장인 사용자는 의식하지 못한다), 뒤는 같은 `card_label` 에 다른 `header_hash` 파일이 오면 완료 요약에 경고를 띄워 잡는다 — 이미 계산하는 값 하나를 재사용하므로 추가 비용이 없다. 카드 목록을 위한 테이블은 만들지 않는다. `SELECT DISTINCT card_label FROM upload_jobs` 가 곧 목록이라 마이그레이션·CRUD 화면·고아 레코드가 전부 사라진다.

### ADR-004: 신호 임계값을 상수로 못 박는다
**결정**: 5종의 임계값을 `thresholds.ts` 상수로 고정한다. 사용자 설정도, 통계적 자동 조정도 하지 않는다. 각 신호는 비율과 절대액 **두 조건의 AND**로 잡는다.
**이유**: 신호가 결정론적이어야 테스트할 수 있다. 임계값이 사용자마다 다르면 "왜 이건 안 잡혔나"를 재현할 수 없다. 조건이 둘인 이유는 비율만 쓰면 2,000원 → 8,000원이 `+300%`로 걸리고, 절대액만 쓰면 30만원 식비의 3만원 변동이 걸리기 때문이다. 알림 피로가 이 기능을 죽이는 가장 흔한 방식이라 오탐을 줄이는 쪽으로 기울였다.
**트레이드오프**: 소비 규모가 아주 크거나 작은 사용자에게는 임계값이 맞지 않는다. 신호가 하나도 안 뜨거나 너무 많이 뜰 수 있다. MVP는 이를 감수하고, 값 조정은 실사용 데이터를 본 뒤에 한다 — 그래서 한 파일에 모았다. `small_frequent`(소액 다발)도 같은 이유로 미뤘다. 유용한 각도이지만 건당 상한과 월 합계 하한을 실사용 분포 없이 정할 근거가 없다.

### ADR-005: 체험 만료는 쓰기만 막고 읽기는 전부 허용한다
**결정**: 7일 체험이 끝나면 업로드·리포트 생성·분류 수정(쓰기)을 막고, 기존 대시보드·리뷰·리포트 열람은 전부 허용한다. 판정은 `entitlement.ts` 한 곳에서 매 요청 계산한다.
**이유**: 업로드를 허용하는 순간 가맹점 분류 LLM 비용이 무수익 사용자에게서 계속 나간다. 반대로 읽기를 막으면 사용자가 이미 만든 결과물을 인질로 잡는 셈이라 재방문 자체가 끊긴다. 쓰기만 막으면 비용은 정확히 0이 되고, 대시보드가 체험 종료 시점에 얼어붙어 "계속 보려면 결제"라는 압박이 자연스럽게 생긴다.
**트레이드오프**: 결제하지 않는 사용자의 데이터를 계정 삭제 전까지 계속 보관하게 된다(ADR-009와 같은 방향의 비용이다). 검증 대상이 "읽기 게이트를 빠뜨렸나"가 아니라 **"쓰기 경로마다 게이트를 걸었나"**가 되므로, 권한 매트릭스를 화면이 아니라 동작 단위로 테스트해야 한다.

### ADR-006: 월간 리포트는 업로드가 아니라 사용자가 재생성한다
**결정**: 업로드 파이프라인이 리포트를 자동으로 다시 만들지 않는다. 스케줄러도 두지 않는다. 리포트 화면에 **생성 시각(`generated_at`)과 "다시 만들기" 버튼을 항상** 띄우고, 다시 만들지는 사용자가 정한다.
**이유**: 업로드가 리포트를 자동 생성하면 **한 달치 명세서를 나눠 올리는 사용자에게 LLM 호출이 업로드 횟수만큼 발생한다.** 중간 시점의 리포트는 데이터가 덜 찬 상태로 만들어졌다가 덮어써지므로, 그 호출들은 전부 버려지는 비용이다. `is_stale` 플래그를 두고 파이프라인이 세우게 하는 안도 있었으나, "3월 12일에 생성됨"이라는 사실 하나로 사용자는 그 뒤에 올린 파일이 반영되지 않았음을 알 수 있다. 컬럼 하나와 파이프라인 한 단계를 줄이려고 잃는 것이 없다.
**트레이드오프**: 화면에 버튼 하나가 는다. 사용자가 다시 만들기를 누르지 않으면 낡은 리포트를 계속 보게 되므로 생성 시각을 눈에 띄게 둔다. 같은 달 생성을 두 번 누르면 LLM이 두 번 호출되므로 생성 중 상태를 서버에서 확인해 중복 요청을 막는다.

### ADR-007: 결제는 로그인 이후에만 열린다
**결정**: 랜딩의 가격 섹션 CTA는 구글 로그인으로 보낸다. Polar 체크아웃은 로그인된 대시보드 안에서만 생성한다.
**이유**: 체크아웃 생성 시 `user_id`를 metadata에 실어야 웹훅이 도착했을 때 어느 계정에 권한을 켤지 알 수 있다. 비로그인 결제를 받으면 이메일로 계정을 추정해 병합하는 로직이 필요해지고, 다른 구글 계정으로 로그인한 사용자를 처리할 방법이 없다.
**트레이드오프**: 결제까지의 클릭 수가 늘어난다. 7일 체험이 있어 가입 전 결제할 이유가 없으므로 실질 손해는 작다.

### ADR-008: 세 종류의 LLM 호출에 서로 다른 모델을 쓴다
**결정**: 가맹점 분류는 `gpt-5.6-luna`, 컬럼 매핑 추론과 신호 서술은 `gpt-5.6-terra`. 모델명은 `src/services/openai.ts` 상수 한 곳에만 둔다.
**이유**: 분류는 호출량이 가장 많아 비용 지배적이고 오답의 피해가 국소적이다(가맹점 하나의 카테고리). 컬럼 매핑은 호출량이 적지만 틀리면 거래 전체가 엉뚱한 달로 가고 그 오답이 개인 캐시에 굳는다. 서술은 사용자가 직접 읽는 유일한 출력이라 문장 품질이 곧 제품 품질이다.
**단가 근거**(2026-08 조회, per 1M tokens): luna $0.20/$1.20, terra $2.00/$12.00, sol $5.00/$30.00. 가맹점 100개 배치 1회를 luna로 처리하면 약 5원, terra면 약 47원이다. 첫 업로드(미매칭 300개 ≈ 3배치) 기준 분류 15원 + 매핑 5원 + 서술 18원 ≈ 38원.
**주의**: **Batch API의 50% 할인은 이 파이프라인에 쓸 수 없다.** 업로드 진행률을 2초 폴링으로 보여주는 구조라 최대 24시간 지연되는 비동기 배치와 양립하지 않는다. 반면 prompt caching은 분류 시스템 프롬프트(카테고리 10종 정의)가 매 배치 동일해 자동으로 걸린다.
**트레이드오프**: 모델이 둘이라 프롬프트 튜닝과 테스트 모킹 대상이 늘어난다. 매핑을 `gpt-5.6-sol`로 한 단계 더 올리는 안도 있었으나(형식당 12원) 개인 캐시가 이 경로의 호출을 대부분 흡수해 실측 없이 값어치를 판단할 수 없어 보류했다. 매핑 실패율이 관측되면 sol로 올리는 것이 첫 번째 조정이다.

### ADR-009: 원본 CSV를 계정 삭제 시까지 보관한다
**결정**: 파싱이 끝난 뒤에도 원본 파일을 Storage에 남긴다. **자동 삭제 cron을 두지 않는다.** 계정 삭제 시 Storage 객체까지 함께 지우고, 사용자는 업로드 목록에서 개별 파일을 언제든 삭제할 수 있다.
**이유**: 파싱 로직이나 매핑 추론을 개선했을 때 과거 업로드를 재처리할 수 있어야 한다. ADR-001이 자동 추론을 택한 이상 재파싱 여지는 실질적 안전망이다. 보관 기한을 두는 안(해지 후 N일 뒤 삭제)은 그 안전망을 갉아먹으면서 cron을 하나 요구하는데, 그 크론이 조용히 죽으면 어차피 정책이 지켜지지 않는다.
**트레이드오프**: **실제 카드 명세서 원본이 무기한 쌓인다. 이 프로젝트가 감수하는 가장 큰 위험이다.** 네 겹으로 상쇄한다 — ① 버킷은 private이고 읽기는 service role(Inngest 워커)만 ② 원본 파일이 애플리케이션 서버를 통과하지 않는다(클라이언트 → Storage 직행) ③ Storage 경로에 `user_id`를 넣고 다운로드는 소유자 확인 후 60초 서명 URL로만 ④ 계정 삭제 시 Storage 객체까지 지운다.
**주의**: **계정 삭제가 원본의 유일한 삭제 경로다.** 삭제 크론이 없으므로 이 코드에 대체재가 없다. 구현하지 않으면 보관 정책이 그대로 "영구 보관"이 된다.

### ADR-010: 백그라운드 job은 Inngest로 처리하고 스텝을 잘게 쪼갠다
**결정**: 업로드 분석 파이프라인을 Inngest 스텝 함수로 구현하고, 워커 코드는 Next.js 저장소 안에 두고 `/api/inngest`로 노출한다. **오래 걸리는 일은 스텝을 잘게 쪼개 각 호출이 함수 실행시간 안에 들어오게 한다** — LLM 분류는 배치 1개당 스텝 1개다.
**이유**: 이 파이프라인에서 MVP를 가장 자주 망가뜨리는 건 OpenAI 호출 실패로 job이 좀비가 되는 것인데, Inngest는 스텝별 재시도·상태 추적·실행 로그를 그대로 제공한다. 직접 구현하면 그 상태 머신이 분류 로직보다 길어진다.
**주의**: **Inngest는 실행시간을 늘려주지 않는다.** 각 스텝은 `/api/inngest`로 들어오는 별도 요청이므로 **스텝 하나하나가 Vercel 함수 제한을 그대로 받는다.** 한 스텝 안에서 배치를 루프로 돌면 거래량에 비례해 죽는다. Inngest가 파는 것은 시간이 아니라 재시도와 관측이다.
**트레이드오프**: 외부 서비스 의존이 하나 늘고 벤더 종속이 생긴다. 스텝을 쪼개면 파이프라인이 배치 수를 먼저 계산해 동적으로 스텝을 도는 구조가 되어 한 겹 복잡해진다. 대안이던 Vercel Cron + jobs 폴링은 의존성이 0이지만 Cron 주기 제약으로 Pro 플랜이 사실상 전제되고 재시도·중복 실행 방지를 직접 짜야 했다. Supabase Edge Functions는 원본이 Vercel을 안 거치는 장점이 있었으나 Node/Deno 두 런타임에 파서와 타입이 갈라지는 비용이 컸다.

### ADR-011: 배포는 mock 단계부터, push 자동 배포로
**결정**: Vercel 배포를 마지막 step으로 미루지 않는다. **첫 step에서 Next.js 골격이 서는 즉시 Vercel에 link하고, 내용이 mock 랜딩뿐인 상태로 첫 배포를 끝낸다.** GitHub 저장소를 연결해 `main` push → production, 브랜치·PR → preview가 자동으로 돌게 한다. 마지막 step에는 랜딩 완성과 env·endpoint·Protection 최종 검증만 남긴다.
**이유**: 배포를 마지막에 두면 **로컬에서만 통과하는 상태로 전 step을 쌓게 된다.** 이 프로젝트에서 배포 환경은 부수적 관심사가 아니라 설계 전제다 — ADR-010의 스텝 분할은 "Vercel 함수 실행시간 제한"을 전제로 만든 구조이고, `/api/inngest`는 외부에서 호출되는 엔드포인트라 Deployment Protection과 정면으로 충돌할 수 있다. 이 전제들은 배포본에서만 확인된다. 첫 배포는 내용이 비어 있어도 값어치가 있는데, **검증 대상이 앱이 아니라 배포 경로 자체**이기 때문이다.
**트레이드오프**: 미완성 앱의 URL이 개발 첫날부터 존재한다. Deployment Protection으로 막지만 **그 Protection이 나중에 Inngest 연동 step에서 워커 호출을 막는 원인이 된다** — 이 충돌을 앞에서 만나는 것 자체가 목적이다. 또 배포 실패가 곧 개발 중단이 될 수 있고, 배포 설정이 첫 step과 마지막 step 두 곳에 갈려 어느 쪽이 무엇을 책임지는지 step 파일에 명시해야 한다.
