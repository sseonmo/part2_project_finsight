# Architecture Decision Records

## 철학
MVP 속도 최우선. 다만 **개인 금융 데이터를 다루므로 정확성과 데이터 경계는 속도와 바꾸지 않는다.** 틀린 숫자를 그럴듯하게 보여주느니 모른다고 말한다. 외부 의존성은 직접 만들면 더 나빠질 것만 들인다.

---

### ADR-001: 백그라운드 job을 Inngest로 처리
**결정**: 업로드 분석 파이프라인을 Inngest 스텝 함수로 구현한다. 워커 코드는 Next.js 저장소 안에 두고 `/api/inngest` 로 노출한다. **오래 걸리는 일은 스텝을 잘게 쪼개 각 호출이 함수 실행시간 안에 들어오게 한다** — LLM 분류는 배치 1개당 스텝 1개다.
**이유**: 이 파이프라인에서 MVP를 가장 자주 망가뜨리는 건 OpenAI 호출 실패로 job이 좀비가 되는 것인데, Inngest는 스텝별 재시도·상태 추적·실행 로그를 그대로 제공한다. 직접 구현하면 그 상태 머신이 분류 로직보다 길어진다.
**주의**: Inngest는 실행시간을 늘려주지 않는다. 각 스텝은 `/api/inngest` 로 들어오는 별도 요청으로 실행되므로 **스텝 하나하나가 Vercel 함수 제한을 그대로 받는다.** 한 스텝 안에서 배치를 루프로 돌면 거래량에 비례해 죽는다. Inngest가 파는 것은 시간이 아니라 재시도와 관측이다.
**트레이드오프**: 외부 서비스 의존이 하나 늘고 벤더 종속이 생긴다. 스텝을 잘게 쪼개면 파이프라인 코드가 배치 수를 먼저 계산해 동적으로 스텝을 도는 구조가 되어 한 겹 복잡해진다. 대안이던 Vercel Cron + jobs 테이블 폴링은 의존성이 0이지만 Cron 주기 제약으로 Pro 플랜이 사실상 전제되고 재시도·중복 실행 방지를 직접 짜야 했다. Supabase Edge Functions는 원본 파일이 Vercel을 아예 안 거치는 장점이 있었으나 Node/Deno 두 런타임에 파서와 타입이 갈라지는 비용이 컸다.

### ADR-002: 하이브리드 분류 + 전역 가맹점 캐시
**결정**: 가맹점명 정규화 → 개인 오버라이드 → 전역 캐시 `merchant_categories` → 시드 룰 → OpenAI 배치 순으로 매칭한다. LLM 호출은 **미매칭 고유 가맹점 100개 배치** 단위로만 한다.
**이유**: 개인 가계부는 객단가가 낮아 거래 1건당 LLM 비용이 곧 마진이다. 거래 500건은 고유 가맹점 80개 남짓이고, 캐시가 전역이라 사용자가 쌓일수록 미스율이 떨어진다. 개인 소비의 가맹점 분포는 상위 집중이라 캐시 효과가 크다. MVP 콜드스타트는 국내 주요 가맹점 150개 안팎을 시드로 미리 채워 막는다.
시드 룰은 테이블이 아니라 `src/lib/merchant-rules.ts` 상수로 둔다. 150개 남짓이라 코드로 충분하고, 마이그레이션·시드 SQL·조회 쿼리가 통째로 사라지며 순수 함수로 테스트할 수 있다.
**트레이드오프**: 정규화 품질에 캐시 적중률이 통째로 걸린다(지점명·PG사 접두어 처리를 틀리면 캐시가 무너진다). 전 거래를 LLM에 맡기는 편이 구현은 단순하고 정확도도 높지만 거래량에 비례해 비용이 선형 증가한다. 사용자 수정을 전역 캐시에 반영하지 않기로 해서 잘못된 전역 분류가 자동으로 고쳐지지는 않는다 — 수정 반복은 로그로만 남긴다.

### ADR-003: 리포트와 인사이트의 수치는 SQL 집계 전용
**결정**: 카테고리별 합계·건수·전월 대비 증감·상위 가맹점은 전부 SQL로 계산하고, LLM에는 그 집계 JSON만 넘겨 서술 문단만 받는다. UI에서도 수치는 집계값을 직접 렌더한다. AI 리뷰의 인사이트 카드와 거래별 코멘트에도 같은 규칙이 그대로 적용된다.
**이유**: LLM은 합계를 틀려도 문장은 그럴듯하게 쓴다. "지난달보다 12% 덜 쓰셨네요"가 틀린 숫자면 가계부 앱의 신뢰가 한 번에 무너진다. 거래 원본을 통째로 넣으면 토큰도 수만 개로 뛴다.
**트레이드오프**: LLM이 볼 수 있는 정보가 집계 결과로 제한돼, 미리 계산해 넣지 않은 각도의 통찰은 나오지 않는다. 집계 쿼리를 추가할 때마다 프롬프트도 함께 손봐야 한다.

### ADR-004: 원본 CSV를 구독 중 무기한 보관
**결정**: 원본 CSV를 Supabase Storage(private)에 보관한다. 구독 해지 시 30일 유예 후 원본만 삭제하고 파싱된 거래 데이터는 유지한다. 계정 삭제 시 전체 즉시 삭제하며, 사용자는 업로드 목록에서 개별 파일을 언제든 지울 수 있다. 원본은 소유자 확인을 거친 서명 URL로만 접근한다. **삭제는 Inngest cron 함수 `purge-expired-originals` 가 매일 실행한다.**
**이유**: 분류 결과를 의심할 때 원본과 대조할 수 있어야 하고, 파서를 고친 뒤 재파싱하려면 원본이 필요하다. 삭제에 실행 주체를 명시한 것은, 보관 정책에서 실제로 지켜지지 않는 쪽이 항상 삭제이기 때문이다 — 지우겠다고 적고 지우는 코드가 없으면 개인 금융 데이터가 영구히 남는다.
**트레이드오프**: 개인 금융 데이터를 장기 보관하는 책임이 생기고 유출 시 피해 범위가 커진다. 이를 상쇄하려고 원본 파일이 애플리케이션 서버를 통과하지 않게 했다 — 업로드는 서명 URL로 클라이언트에서 Storage로 직행하고, 읽기는 Inngest 워커만 한다. 삭제를 크론에 맡겼으므로 크론이 조용히 죽으면 정책이 지켜지지 않는다. 실행 로그로 확인할 수 있게 하고 삭제 실패 건은 다음 실행에서 재시도한다.

### ADR-005: 로그인은 Google OAuth 단독
**결정**: Supabase Auth의 Google OAuth만 지원한다.
**이유**: 비밀번호를 아예 다루지 않는 것 자체가 금융 데이터 앱에서 리스크 감소다. 재설정·검증 플로우를 만들지 않아도 되고 구현이 가장 얇다.
**트레이드오프**: 구글 계정이 없거나 쓰고 싶지 않은 사용자를 통째로 잃는다. 나중에 매직링크를 추가할 수는 있으나 그 시점에 기존 계정 병합을 고민해야 한다.

### ADR-006: AI 리뷰는 SQL이 짚고 LLM은 말만 한다
**결정**: "평소와 다른 소비"를 결정론적 SQL 신호 5종(`category_spike`, `new_merchant_large`, `outlier_transaction`, `recurring_payment`, `recurring_price_up`)으로 탐지하고, 무엇을 먼저 보여줄지는 **원화 영향도 점수**로 정렬한다. LLM은 이미 선별된 신호를 받아 문장으로 옮기는 일만 한다. 임계값은 `src/lib/signals/thresholds.ts` 상수 하나에 모으고, 업로드당 LLM 호출은 1회(배치)만 늘린다.
**이유**: ADR-003이 "수치를 LLM이 만들지 않는다"를 막았다면, 여기서 막는 것은 **"무엇을 지적할지를 LLM이 고르는 것"**이다. 거래 원본을 넘기고 "특이한 것을 찾아줘"라고 하면 같은 데이터에서 매번 다른 지적이 나오고, 근거가 약한 신호를 그럴듯한 문장이 덮어버린다. 탐지가 SQL이면 결과가 재현되고 경계값을 픽스처로 고정해 테스트할 수 있다. 알림 피로가 이 기능을 죽이는 가장 흔한 방식이라, 각 신호를 비율과 절대액 두 조건의 AND로 잡아 오탐을 줄이는 쪽으로 기울였다.
**영향도가 없는 신호**: `recurring_payment` 에는 영향도를 매기지 않고 인사이트 카드·코칭 문단에서 제외한다(`impact` 는 nullable, 선정 쿼리에 `impact IS NOT NULL`). "구독을 쓰고 있다"는 것은 평소와 다른 소비가 아니라 평소 그 자체라 이 ADR이 정의한 탐지 대상이 아니다. 월 금액 × 12 같은 값을 억지로 매기면 같은 구독이 매달 카드 1위를 차지해, 이 ADR이 줄이려던 알림 피로를 직접 만들게 된다. 변화인 `recurring_price_up`(인상)만 카드에 올린다. 이 신호는 `/dashboard/subscriptions` 표에서 SQL로만 렌더되므로 `narrative` 도 생성하지 않는다.

**`period` 규약**: 신호의 `period` 는 **그 신호를 뒷받침하는 관측 구간의 마지막 달**이다. `recurring_*` 처럼 3개월을 보는 신호도 마지막 달에 귀속시키고, 반복 지출 목록은 `(user_id, type, 대상 키)` 별 최신 `period` row 하나만 읽는다. 최초 발견 달에 고정하는 안은 신호가 과거에 묶여 "지속 개월"이 갱신되지 않는다. 매달 row가 하나씩 늘지만 유니크 키가 달을 포함하므로 이는 정상 동작이고, 조회는 최신 1건만 본다.

**누적 규칙**: 같은 달을 다시 업로드해도 기존 신호를 지우지 않고 새로 발생한 것만 추가한다. 지우고 다시 계산하는 편이 정확하지만, 그러려면 숨김 기록을 별도 테이블로 빼고 동시 업로드의 삭제·삽입 경합까지 다뤄야 한다. MVP에서는 명세서를 여러 장 쓰는 사용자의 신호가 조금 낮게 잡히는 쪽을 택했다.

**MVP에서 뺀 것**: `long_running_recurring`(12개월 지속)은 그만큼의 데이터를 올리는 사용자가 초기에 없어 구현해도 뜨지 않는다. `category_record`(관측 이래 최대)는 `category_spike` 와 겹치는 경우가 대부분이다. 거래별 코멘트도 인사이트 카드와 내용이 겹쳐 뺐다. 셋 다 신호 파이프라인이 자리 잡은 뒤 추가하는 것이 순서상 맞다.
**트레이드오프**: **LLM이 스스로 발견하는 통찰은 포기했다.** 우리가 쿼리로 미리 정의한 5가지 신호 밖의 패턴은 영영 나오지 않고, 새 각도를 추가하려면 매번 쿼리·임계값·테스트를 함께 짜야 한다. 임계값 숫자들은 전부 추측이라 실사용 데이터로 조정이 필요하다 — 그래서 한 파일에 모았다. `dormant_recurring`("안 쓰는 구독")은 폐기했다. CSV 거래 내역에는 구독을 쓰고 있는지가 찍히지 않아 판정 근거가 없고, 근거 없는 신호를 두면 LLM이 추측으로 채우게 되어 이 ADR이 막으려던 것을 그대로 되살린다. 대신 나중에 `long_running_recurring` 을 추가하면 "14개월째, 누적 238,000원"이라는 사실만 제시하고 판단은 사용자가 하게 한다.

### ADR-007: 금액은 지출을 양수로 저장하고 입금은 종류로 구분
**결정**: `transactions.amount` 는 항상 지출 금액(양수)이다. 입금·환불·취소는 `transaction_type` 으로 구분하고 지출 집계에서 제외한다. CSV 원본의 부호는 파싱 단계에서 이 규약으로 정규화한다.
**이유**: 카드 명세서는 지출을 양수로, 은행 거래내역은 출금을 음수로 쓴다. 원본 부호를 그대로 담으면 한 테이블 안에 두 규약이 섞여 카테고리 합계·전월 대비·신호 탐지가 전부 "이 행의 부호가 어느 쪽 규약인가"를 다시 판단해야 한다. 부호를 입구에서 한 번 정규화하면 이후 모든 집계가 `SUM(amount)` 로 끝나고, 신호 임계값(30,000원 이상 같은)도 부호를 신경 쓰지 않는다.
**트레이드오프**: **환불이 원래 지출을 상쇄하지 않는다.** 3월에 30만원을 쓰고 15만원을 환불받아도 3월 쇼핑은 30만원으로 남고 환불은 별도로 표시된다. 사용자의 체감 순지출과 어긋날 수 있다. 환불을 음수 지출로 담으면 이 문제는 사라지지만, 카테고리 월 합계가 음수가 될 수 있어 `category_spike` 의 비율 계산과 `outlier_transaction` 의 비중 계산에 0·음수 분모 예외가 신호마다 생긴다. 정확도 손실을 한 곳(환불 표시)에 가두는 쪽을 택했다.

### ADR-008: LLM 모델은 호출 지점별로 나눈다
**결정**: 세 군데 LLM 호출에 같은 모델을 쓰지 않는다. **가맹점 분류는 `gpt-5.6-luna`, 컬럼 매핑 추론과 리포트·신호 서술은 `gpt-5.6-terra`** 를 쓴다. 모델명은 `src/services/openai.ts` 상수 한 곳에 모아 호출 지점이 직접 문자열을 들고 있지 않게 한다.
**이유**: 세 호출은 비용 구조와 실패 비용이 정반대다. 분류는 미매칭 가맹점 수에 비례해 호출이 늘어 **비용을 지배하지만**, 출력이 카테고리 10종 enum이라 모델을 올려도 얻을 정확도가 얼마 없다. 컬럼 매핑은 CSV 형식당 1회뿐이라 **비용이 사실상 0인데 틀리면 가장 비싸다** — 날짜 컬럼을 잘못 고르면 거래 전체가 엉뚱한 달로 들어가고, 그 오답이 개인 fingerprint 캐시에 굳어 매달 재현된다. 서술은 사용자가 직접 읽는 유일한 출력이라 문장 품질이 곧 제품 품질이다. 분류만 최저가로 내리면 비용의 대부분이 사라지고, 나머지 둘은 상위 모델을 써도 절대액이 무시할 수준이다.
**단가 근거**(2026-08 조회, per 1M tokens): luna $0.20/$1.20, terra $2.00/$12.00, sol $5.00/$30.00. 가맹점 100개 배치 1회를 luna로 처리하면 약 5원, terra면 약 47원이다. 첫 업로드(미매칭 300개 ≈ 3배치) 기준 분류 15원 + 매핑 5원 + 서술 18원 ≈ 38원.
**주의**: **Batch API의 50% 할인은 이 파이프라인에 쓸 수 없다.** 업로드 진행률을 2초 폴링으로 보여주는 구조라 최대 24시간 지연되는 비동기 배치와 양립하지 않는다. 반면 prompt caching은 분류 시스템 프롬프트(카테고리 10종 정의)가 매 배치 동일해 자동으로 걸린다.
**트레이드오프**: 모델이 둘로 갈려 프롬프트도 두 벌을 관리하게 된다 — 분류 프롬프트를 luna에 맞춰 조이면 terra로 올릴 때 그대로 쓸 수 없다. 분류 정확도가 실제로 부족한지는 실사용 전엔 모르며, 틀린 분류는 전역 캐시에 저장되어 다른 사용자에게도 퍼진다(ADR-002). 컬럼 매핑을 `gpt-5.6-sol` 로 한 단계 더 올리는 안도 있었으나(형식당 12원, 여전히 미미) 개인 캐시가 이 경로의 호출을 대부분 흡수해 실측 없이 값어치를 판단할 수 없어 보류했다. 매핑 실패율이 관측되면 sol 로 올리는 것이 첫 번째 조정이다.

### ADR-009: 배포는 mock 단계부터, push 자동 배포로
**결정**: Vercel 배포를 마지막 step으로 미루지 않는다. **step 0에서 Next.js 골격이 서는 즉시 Vercel CLI로 프로젝트를 link하고, 내용이 mock 랜딩뿐인 상태로 첫 배포를 끝낸다.** 이어서 GitHub 저장소를 연결해 `main` push → production, 브랜치·PR → preview 가 자동으로 돌게 한다. 이후 step은 배포를 위해 아무것도 하지 않는다. 마지막 step 17(`landing-launch`)에는 랜딩 완성과 **전체 env 주입·endpoint·Protection 최종 검증만** 남긴다.
**이유**: 배포를 마지막에 두면 **로컬에서만 통과하는 상태로 17개 step을 쌓게 된다.** 그리고 이 프로젝트에서 배포 환경은 부수적 관심사가 아니라 설계 전제다 — ADR-001의 스텝 분할은 애초에 "Vercel 함수 실행시간 제한"을 전제로 만든 구조이고, `/api/inngest` 는 외부에서 호출되는 엔드포인트라 Deployment Protection과 정면으로 충돌할 수 있다. 이 전제들은 배포본에서만 확인된다. 첫 배포는 내용이 비어 있어도 값어치가 있는데, **검증 대상이 앱이 아니라 배포 경로 자체**이기 때문이다 — 빌드 통과, 링크, 자동 배포 트리거, 접근 정책은 mock으로 전부 확인된다.
**배포 step을 따로 만들지 않은 이유**: step 사이에 배포 step을 끼우면 뒤 번호가 전부 밀리고, `plan.md` 5절이 step을 번호로 참조하는 표 40여 개 항목이 통째로 어긋난다. 번호 체계를 지키는 편이 계획 문서의 신뢰도에 낫다.
**트레이드오프**: 미완성 앱의 URL이 개발 첫날부터 존재한다. Deployment Protection으로 본인만 접근 가능하게 막지만, **그 Protection이 나중에 step 9에서 Inngest 연동을 막는 원인이 된다** — 이 충돌을 미루지 않고 앞에서 만나는 것 자체가 이 ADR의 목적이다. 또 step 0부터 배포가 걸려 있으면 배포 실패가 곧 개발 중단이 될 수 있고, 배포 설정이 step 0과 17 두 곳에 갈려 어느 쪽이 무엇을 책임지는지 step 파일에 명시해야 한다. 반대안이던 "step 17에 몰아넣기"는 앞 16개 step이 배포를 신경 쓰지 않아도 되는 대신, 실패가 발견되는 시점이 되돌릴 시간이 가장 없는 때다.
