# UX 가이드라인

이 문서는 **"왜 이 순서인가, 어떻게 다음 단계로 넘기는가"**의 단일 출처다. 화면을 배치하고 문구를 정할 때 여기 적힌 원칙과 단계를 따른다.

## 출처와 효력

원칙 7종은 [Figma — UI 디자인 원칙](https://www.figma.com/ko-kr/resource-library/ui-design-principles/)에서 가져왔고, 각 원칙을 이 제품의 화면·데이터·사용자로 번역한 것이 1부다. 일반론을 옮겨 적지 않고 **이 앱에서 무엇을 하라는 뜻인지**까지 내렸다.

저장소에 단일 출처가 이미 둘 있다. 경계는 이렇다.

| 문서 | 맡는 것 | 부딪히면 |
|---|---|---|
| `USER_FLOW.md` | 무엇이 있는가 — 화면·상태 전이·차단 규칙 | **USER_FLOW가 이긴다** |
| `DESIGN.md` | 어떻게 보이는가 — 색·타이포·간격 값 | **DESIGN이 이긴다** |
| 이 문서 | 왜 이 순서인가 — 배치·순서·문구·유도 | 위 둘의 빈자리만 |

이 문서가 새 화면이나 새 상태를 제안하면 그것은 **`USER_FLOW.md` 갱신 요청**이지 이 문서의 결정이 아니다. 3부의 갭 진단이 그 목록이다.

PRD "디자인" 네 줄(도구처럼 보인다 / 무채색 기본 / 숫자가 주인공 / 밀집형)이 상위 원칙이고, 아래 7원칙은 그것과 충돌하지 않는 범위에서만 작동한다. 충돌하면 PRD가 이긴다.

# 1부 — 원칙

## 1. 계층 구조 (Visual Hierarchy)

**이 앱에서:** 한 화면에는 1차 정보가 하나다. 대시보드는 그 달의 총 지출, 신호 상세는 그 신호의 판정 금액, 완료 요약은 새로 추가된 거래 수다.

- 금액은 화면에서 가장 먼저 읽힌다. 라벨·테두리·부가 설명은 그보다 약하다 (`DESIGN.md` 원칙 3)
- **사용자가 읽을 수 없는 문자열을 1차 자리에 두지 않는다.** job UUID, 파일 해시, 내부 상태 문자열은 화면에 있더라도 가장 약한 층이다
- 한 패널에 `h2`가 둘이면 패널이 둘이어야 한다

**위반 예:** 진행률 카드 헤더에 job ID가 제목과 나란한 크기로 놓이는 것. 사용자는 그 문자열로 아무것도 하지 못한다.

## 2. 점진적 공개 (Progressive Disclosure)

**이 앱의 중심 원칙이다.** 업로드와 신호가 둘 다 이미 3층 구조이기 때문이다.

```
업로드   다이얼로그(파일·카드)  →  진행률 카드(지금 뭘 하는 중)  →  완료 요약(네 숫자)
신호     인사이트 카드(상위 3개) →  리뷰 목록(그 달 전부)          →  신호 상세(근거 거래·판정 조건)
```

규칙은 하나다. **지금 결정에 필요한 것만 보이고, 근거는 한 번 더 눌러야 나온다.**

- 정상 경로에 확인 단계를 늘리지 않는다. 컬럼 매핑 확인 화면은 `needs_mapping`일 때만 뜬다 (ADR-001)
- **처음 하는 일과 반복하는 일을 같은 무게로 보여주지 않는다.** "CSV 받는 법"은 첫 업로드에 펼쳐져 있고, 두 번째부터는 접혀 있다
- 대기는 숨기지 말고 지금 무엇을 하는 중인지로 바꾼다 ("거래 내역을 읽는 중" → "카테고리를 분류하는 중")
- 남은 단계 수를 감추지 않는다. 3단계짜리 일에는 몇 번째인지가 보인다

**위반 예:** 다섯 개 카드사 CSV 다운로드 경로가 열 번째 업로드에도 똑같이 펼쳐져 있는 것.

## 3. 일관성 (Consistency)

**약속과 이행이 같은 단어를 써야 한다.** 랜딩에서 본 계단과 앱 안에서 밟는 계단이 다르면, 호기심이 이행으로 이어지지 않는다.

- **계단은 하나다.** 랜딩의 3단계, 빈 대시보드의 3단계, 시작하기 카드의 3단계는 **같은 세 문구**여야 한다 (2부 "계단은 하나다")
- **같은 개념에 같은 단어를 쓴다.** 아래가 정본이다

| 정본 | 쓰지 않는 말 |
|---|---|
| **명세서** (사용자가 올리는 것) | 내역서, 거래내역 파일, 데이터 |
| **CSV 파일** (파일 형식을 말할 때만) | 엑셀, 시트 |
| **거래** (저장된 행 하나) | 트랜잭션, 내역, 건 |
| **가맹점** | 상점, 머천트, 사용처 |
| **분류** (카테고리를 붙이는 일) | 카테고라이징, 태깅 |
| **리뷰** (신호를 모아 보는 화면) | 인사이트 페이지, 분석 |
| **신호** (탐지된 항목 하나) | 알림, 경고, 이슈 |

- 같은 동작에 같은 버튼을 쓴다. 업로드를 여는 버튼은 어느 화면에서든 `명세서 올리기`다
- 기존 패턴을 벗어날 때는 그 자리에 근거를 적는다

## 4. 대비 (Contrast)

**이 앱에서:** 색이 붙는 곳은 세 군데뿐이다 — 카테고리 구분, 증감 표시, 위험한 동작. 나머지는 무채색이다 (`DESIGN.md` 원칙 2).

- **화면당 primary 버튼은 하나다.** 그 화면의 목표 하나에만 붙는다
- 목표가 아닌 동작은 secondary·ghost로 내린다. 크기까지 같이 내린다
- **되돌릴 수 없는 동작에만 `danger`를 쓴다** — 계정 삭제, 업로드 삭제. 자주 쓰는 동작에 붙이면 경고가 배경이 된다
- 색만으로 의미를 전달하지 않는다. 증감은 색 + 부호(`+`/`−`)를 함께 쓴다

**위반 예:** 거래 0건인 사용자의 화면에 `명세서 올리기`와 `요금제 보기`가 같은 크기로 나란히 놓이는 것. 그 화면의 목표는 첫 업로드 하나다.

## 5. 접근성 (Accessibility)

- 텍스트 대비는 WCAG AA(본문 4.5:1, 큰 글자 3:1)를 넘긴다. `DESIGN.md`가 카테고리 색 4개를 측정 근거로 조정한 것이 이 기준이다
- **모달은 세 가지를 지킨다** — 열릴 때 안으로 포커스 이동, Tab이 밖으로 새지 않음, ESC로 닫히고 닫힐 때 원래 버튼으로 포커스 복원
- 모든 입력에 `label`이 붙는다. placeholder는 label을 대신하지 못한다
- 상태 변화는 `role="alert"` 또는 `aria-live`로 읽힌다. 진행률·에러·완료 요약이 대상이다
- 금액·날짜는 `tabular-nums`로 자릿수를 맞춘다. 읽기 편할 뿐 아니라 스크린리더가 아닌 사용자의 비교 실수를 줄인다
- 클릭 대상은 최소 44×44px 영역을 갖는다

## 6. 근접성 (Proximity)

**이 앱에서:** 숫자와 그 숫자의 근거는 붙어 있어야 한다. 떨어지면 사용자는 숫자를 믿지 않는다.

- 신호 문장과 근거 거래는 같은 화면에 있다 (`/dashboard/review/[yearMonth]/[signalId]`, S36)
- 완료 요약의 네 숫자는 한 덩어리다. 카드 오지정 경고는 숫자가 아니므로 그 덩어리 **밖**에 붙는다
- 월 선택 칩은 그 월의 데이터를 보여주는 화면(대시보드·리뷰·리포트)에만 있고, 다른 화면에는 없다
- 관련 없는 것을 여백 없이 붙이지 않는다. 여백은 장식이 아니라 그룹을 만드는 도구다

## 7. 정렬 (Alignment)

- 236px 고정 사이드바 + sticky 헤더가 전역 그리드다. 화면마다 다른 셸을 만들지 않는다
- **숫자는 우측 정렬, 라벨은 좌측 정렬.** 표에서 금액 열이 흔들리면 비교가 불가능하다
- 카드 안의 요소는 같은 왼쪽 선을 공유한다
- 빈 상태도 같은 그리드 안에 놓는다. 화면 한가운데 띄우지 않는다 — 데이터가 채워졌을 때 자리가 흔들린다

# 2부 — 여정

`USER_FLOW.md`의 사용자 유형 U1~U7 위에 **활성화 축**을 얹는다. U는 "어떤 상태인가"이고, V는 "다음에 무엇을 하게 만들 것인가"다.

## 계단은 하나다

랜딩·빈 대시보드·시작하기 카드가 쓰는 **정본 3단계**다. 세 곳이 같은 문구를 쓴다.

| # | 문구 | 사용자가 하는 일 | 그동안 시스템이 하는 일 |
|---|---|---|---|
| 1 | **명세서 올리기** | 카드사에서 내려받은 CSV를 그대로 올린다 | 컬럼을 자동으로 알아보고 거래를 읽는다 |
| 2 | **분류 확인하기** | 카테고리가 맞는지 보고 틀린 것만 고친다 | 가맹점을 10종으로 나누고, 하나를 고치면 같은 가맹점 전부에 반영한다 |
| 3 | **리뷰 읽기** | 지적받은 문장을 열어 근거를 확인한다 | 지출 급증·튀는 결제·구독료 인상을 찾아 문장으로 옮긴다 |

**"자동 분류"는 단계가 아니다.** 사용자가 하는 일이 아니라 1단계와 2단계 사이에 저절로 벌어지는 일이다. 단계 축은 **사용자 행동**으로 통일한다 — 그래야 랜딩의 계단과 앱 안의 계단이 1:1로 이어붙는다.

시작하기 카드는 이 셋만 담는다. V4 이후는 카드가 아니라 **화면 자체**(월 선택 칩의 빈 달, 만료 예고 배너)가 유도한다. 세 단계를 마치면 카드는 영구히 사라지고, 그 뒤로 이 제품은 도구로만 보인다.

## V0 — 방문

| | |
|---|---|
| 대상 | U1 비로그인 방문자 |
| **목표 하나** | 가입 |
| 이탈 원인 | 무엇을 해야 하는지 모른다. "AI 가계부"가 흔해서 차이가 안 보인다 |
| 넘기는 장치 | 정본 3단계 + **각 단계의 실제 화면 미니 목업** |
| 완료 판정 | Google OAuth 완료, `profiles` 생성 |

랜딩이 파는 것은 기능 목록이 아니라 **"이 세 걸음이면 끝난다"는 짧음**이다. 계좌 연동을 하지 않는다는 점도 단점 해명이 아니라 선택 이유로 놓는다 (현재 랜딩의 "왜 계좌를 연동하지 않나" 섹션이 이미 그렇게 되어 있다).

미니 목업은 각 단계 아래에 그 단계의 실제 화면 일부를 넣는다 — 1단계는 업로드 다이얼로그, 2단계는 카테고리 드롭다운이 열린 거래 행, 3단계는 인사이트 카드 한 장이다. **실제 사용자 데이터가 아니라 예시임을 명시한다** (현재 "이런 문장을 받게 됩니다" 섹션이 쓰는 방식과 같다).

목업은 스크린샷이 아니라 **실제 컴포넌트를 예시 데이터로 렌더한 것**이어야 한다. 스크린샷은 화면이 바뀔 때마다 따로 상하고, 상해도 아무도 모른다.

## V1 — 가입 직후, 거래 0건

| | |
|---|---|
| 대상 | U2 |
| **목표 하나** | 첫 업로드 |
| 이탈 원인 | **CSV를 어디서 받는지 모른다.** 이 제품 최대의 이탈 지점이다 |
| 넘기는 장치 | 빈 대시보드 = 시작하기 카드 1단계. `명세서 올리기` primary 하나 |
| 완료 판정 | `upload_jobs`에 `completed` 1건, 거래 1건 이상 |

이 화면에서 **결제 얘기를 꺼내지 않는다.** 아직 제품을 보지 못한 사람에게 요금제를 권하면 목표가 둘이 되고, 대비 원칙상 primary가 둘이 된다. 체험 뱃지("7일 무료 체험")는 안심 정보이므로 남기되 버튼으로 만들지 않는다.

CSV 받는 법은 **다이얼로그 안에서 펼쳐진 채로** 시작한다. 첫 업로드에는 이것이 1차 정보다.

카드 이름은 마찰을 만들지 않는다 — "카드 1"이 채워져 있고 그 자리에서 고칠 수 있다. 카드가 한 장인 사용자는 이 항목을 의식하지 않고 지나간다.

## V2 — 첫 결과

| | |
|---|---|
| 대상 | U3 (거래 있음, 분류 미확인) |
| **목표 하나** | 자기 숫자를 처음 본다 |
| 이탈 원인 | 처리 대기 중 이탈. 완료 요약이 네 숫자로 끝나 다음에 뭘 할지 모른다 |
| 넘기는 장치 | 진행률 카드가 지금 하는 일을 말한다 → **완료 요약 아래에 2단계로 가는 다음 걸음** |
| 완료 판정 | 대시보드에 그 달 총 지출이 렌더됨 |

**완료 요약은 이 여정에서 가장 중요한 순간이다.** 사용자가 처음으로 자기 데이터를 본 직후이고, 여기서 다음 걸음이 없으면 사다리가 끊긴다. 네 숫자 아래에 `분류 확인하기`(→ 거래 목록)를 둔다.

숫자가 0인 항목은 표시하지 않되 **"새로 추가된 거래 0건"은 반드시 표시한다.** 사용자가 가장 혼란스러워하는 경우다.

첫 달 사용자에게 없는 것을 있는 척하지 않는다. 비교할 지난달이 없으면 "다음 달이면 지난달과 비교해 드릴 수 있습니다"라고 적는다 (S29). 이 문장은 V4로 가는 예고이기도 하다.

## V3 — 신뢰

| | |
|---|---|
| 대상 | U3 |
| **목표 하나** | 분류 1건 수정 **또는** 신호 근거 1번 열기 |
| 이탈 원인 | 분류가 틀렸는데 고치는 법을 모른다. 지적 문장을 믿을 근거가 없다 |
| 넘기는 장치 | 시작하기 카드 2·3단계. 인사이트 카드의 `근거 보기` |
| 완료 판정 | `user_category_overrides` 1건 **또는** 신호 상세 화면 진입 1회 |

**이 두 행동이 "이 도구가 맞다"는 확신을 만든다.** 하나는 "내가 고칠 수 있다"이고, 다른 하나는 "이 숫자는 지어낸 게 아니다"다. 둘 중 하나만 해도 통과로 본다 — 신호가 없는 첫 달 사용자는 후자를 할 수 없기 때문이다.

분류 수정은 가맹점 단위로 전파한다 (S4). 한 건씩 고치게 하면 사용자가 같은 작업을 수십 번 반복하고, 반복하는 순간 도구가 아니라 노동이 된다.

지키지 못할 약속을 문구로 쓰지 않는다. 분류를 고쳐도 신호는 다시 계산되지 않으므로, 안내는 "분류를 고치면 대시보드가 다시 계산됩니다"로 **좁혀 적는다** (S37).

## V4 — 습관

| | |
|---|---|
| 대상 | U3 (한 달치만 있음) |
| **목표 하나** | 둘째 달 업로드 |
| 이탈 원인 | 한 달치로는 제품 가치의 절반만 보인다. 다음 달에 다시 올 이유를 못 받았다 |
| 넘기는 장치 | 월 선택 칩의 **빈 달** + 그 달의 빈 상태 문구 |
| 완료 판정 | 서로 다른 `year_month` 2개 이상에 거래 존재 |

**둘째 달이 이 제품의 진짜 활성화 지점이다.** 신호 5종 중 넷이 전월 비교를 전제하므로, 한 달치만 있는 사용자는 `outlier_transaction` 하나만 받는다. 비교가 생기는 순간 가치가 두 배가 아니라 다섯 배가 된다.

시작하기 카드는 여기까지 오지 않는다. 대신 **월 선택 칩이 비어 있는 달을 보여주는 것**이 유도다 — 빈 칸은 채우고 싶어지는 반면, 배너는 닫고 싶어진다.

MVP에는 이메일·푸시가 없다. 그래서 재방문은 전적으로 V2에서 남긴 예고("다음 달이면…")와 월 칩의 빈자리에 달려 있다. 이 둘을 약하게 만들면 대체 수단이 없다.

## V5 — 결제

| | |
|---|---|
| 대상 | U4 체험 만료자 → U5 구독자 |
| **목표 하나** | 만료 전후 전환 |
| 이탈 원인 | 예고 없이 막히면 사용자는 결제가 아니라 고장으로 받아들인다 |
| 넘기는 장치 | 만료 2일 전 예고 배너 → 읽기 전용 배너 → `/dashboard/billing` |
| 완료 판정 | `subscription_status = active` |

**막는 것은 쓰기 전부, 여는 것은 읽기 전부다** (ADR-005). 자기 금융 데이터를 인질로 잡는 제품은 결제가 아니라 탈퇴를 부른다. 읽기를 열어두는 것은 선의가 아니라 전환 설계다 — 볼 수 있어야 아까워진다.

배너 문구는 **잃는 것이 아니라 남는 것**을 먼저 말한다. "기존 데이터는 계속 볼 수 있습니다"가 "새 업로드가 잠깁니다"보다 앞에 오지는 않되, 같은 배너 안에 반드시 함께 있어야 한다.

만료 상태에서도 반복 지출 목록·리뷰·신호 상세는 열린다 (ADR-012). 비용이 들지 않는 기능을 막을 이유가 없고, 오히려 재결제 동기가 된다.

## V6 — 복귀

| | |
|---|---|
| 대상 | U7 오래 비운 사용자 |
| **목표 하나** | 비어 있는 달 메우기 |
| 이탈 원인 | 몇 달치를 한꺼번에 올려야 한다는 부담 |
| 넘기는 장치 | 월 선택 칩의 연속된 빈 달 |
| 완료 판정 | 새 업로드 1건 |

**한 번에 다 올리라고 하지 않는다.** 여러 달이 담긴 CSV 하나면 그 안의 모든 달에 신호가 만들어지므로(S28), 사용자가 할 일은 여전히 "파일 하나 올리기" 하나다. 이 사실을 빈 달 문구에서 말한다.

복귀자는 신규 사용자가 아니다. 시작하기 카드를 다시 띄우지 않는다 — 이미 마친 사람에게 다시 나타나면 진행이 초기화된 것처럼 읽힌다.
