# 알려진 결함

`docs/USER_FLOW.md` 의 시나리오를 브라우저(로컬 Supabase + Inngest dev)로 실행해
찾은 결함 중 아직 고치지 않은 것들이다. ⓐ~ⓖ 는 시나리오 23개 완주에서, ⓘ 는
`docs/BROWSER_TEST_CASES.md` 의 시나리오를 실행하다 나왔다. 나머지 7건은
`fix(upload)`·`fix(dashboard)`·`feat(report)`·`fix(signals)`·`fix(narrative)`·
`fix(progress)` 로 고쳤다 — ⓗ "1 이상인 비율이 원시 실수로 박힌다" 와
ⓙ "업로드가 끝나도 대시보드가 갱신되지 않는다" 가 마지막이다.

전부 **실측으로 확인**했다. 추정으로 적은 항목은 그렇다고 표시한다.

## 중간

### ⓐ 5개월 이전 데이터는 URL 을 직접 쳐야 열린다

`src/components/AppHeader.tsx:141` 이 `months.slice(0, 4)` 로 월 선택 칩을
4개만 그린다. 거래가 있는 달이 12개여도 화면에서 갈 수 있는 곳은 최근 4달뿐이고,
그 이전은 `/dashboard?month=2025-09` 처럼 주소를 직접 입력해야 한다.
데이터가 쌓일수록 접근할 수 없는 달이 늘어난다.

고칠 방향: 넘치는 달을 드롭다운으로 접거나 가로 스크롤로 흘린다.

### ⓑ "이 형식으로 가정했습니다" 가 모든 업로드에 붙는다

`src/lib/csv/date.ts:159` 이 `YYYY-MM-DD` 처럼 **구분이 필요 없는 명백한 ISO**
날짜에도 `ambiguousResolvedBy: "assumed-iso"` 를 붙인다. 그 결과 어떤 CSV 를
올려도 "날짜 형식이 구분되지 않아 이 형식으로 가정했습니다" 경고가 뜬다.
늘 뜨는 경고는 읽히지 않으므로, 진짜 모호한 파일(`03/04/2026`)을 올렸을 때도
사용자가 그냥 넘긴다.

고칠 방향: 연도가 앞에 오고 구분자가 있는 형식은 모호하지 않다고 판정한다
(`ambiguousResolvedBy: null`). 실제로 두 해석이 가능한 경우에만 라벨을 남긴다.

### ⓒ `pending` job 이 영구히 남는다

서명 URL 만 발급되고 파일이 Storage 에 올라오지 않으면 job 이 `pending` 에서
영영 멈춘다. 대시보드에 "업로드 중 15%" 카드가 고정되고, `UploadProgressCard`
가 끝나지 않을 작업을 계속 폴링한다. 세션이 만료돼 401 이 떨어져도 폴링이
멈추지 않는다.

부작용 하나: 이 폴링 때문에 페이지의 `networkidle` 이 영영 오지 않는다.
**브라우저 자동화 스크립트는 `waitUntil: "domcontentloaded"` 를 써야 한다** —
`networkidle` 을 쓰면 30초 타임아웃으로 죽는다.

고칠 방향: `pending` 이 일정 시간(예: 15분) 넘게 지속되면 job 을 `failed` 로
정리하는 Inngest 스케줄을 두고, 폴링에 401 종료 조건을 넣는다.

### ⓙ 엑셀 업로드는 `.xlsx` (OOXML) 만 지원한다

`src/components/UploadDialog.tsx:48` 의 `hasExtension(file, ".xlsx")` 가 확장자로만
거른다. 실제 명세서 하나(`이용대금명세서_20260803.xlsx`, 46건 거래 + 서브헤더 1행 +
합계 4행 + 날짜 없는 할인 2행)로 `sheetToCsv` → `parseCsv` → `applyMapping` →
`runSanityCheck` 를 통과시켜 확인했다(2026-08-31, `.local/` 스크립트로 실측).
sanity 판정은 `{ ok: true }`, 유효 거래 46건, 실패 7건(failureRate 13.2%,
`CSV_FULL_FAILURE_RATE_MAX` 20% 이내)으로 정상 처리된다.

**확인하지 않고 코드로만 추정한 것:** 구형 `.xls`(BIFF) 파일이나, 은행이 흔히
내보내는 확장자만 `.xls`/`.xlsx`인 HTML 표는 지원 대상이 아니다. `readSheet.ts`
가 쓰는 `read-excel-file/browser` 는 OOXML 만 읽으므로 이런 파일은 파싱 단계에서
실패한다. UI 는 안내 문구(`UploadDialog.tsx:338`, "엑셀은 .xlsx 만 됩니다. .xls 로
받아졌다면 CSV 로 저장해 주세요.")로 미리 경고하지만, 확장자만 `.xlsx`로 바뀐
BIFF/HTML 파일은 이 안내를 우회해 통과하고, `UploadDialog.tsx:62-66` 의
`toUploadBlob` 이 그 실패를 잡아 `XLSX_READ_FAILED_MESSAGE`("엑셀 파일을
읽지 못했습니다. 카드사에서 CSV 로 내려받아 올려주세요.")로 바꿔 던지므로
사용자에게는 읽을 수 있는 안내가 뜬다. 다만 원인 에러(`catch` 가 삼키는
라이브러리 예외)가 로깅 없이 버려져, 프로덕션에서 파싱이 왜 실패했는지
추적할 단서가 남지 않는다. 실제 그런 파일로는 테스트하지 않았다.

## 중간 — AI 리뷰의 서술과 우선순위

`docs/BROWSER_TEST_CASES.md` 의 픽스처를 실행하다 나왔다. 화면에는 그럴듯한

### ⓘ 마트 장보기가 구독료 인상으로 잡혀 우선순위 최상단을 차지한다

`detect-recurring` 은 가맹점별로 월 1건씩 연속 3개월, 간격 25~35일이면 반복 결제로
본다. `recurring_price_up` 은 여기에 더해 **직전까지의 금액만** 편차 10% 이내면
성립하므로, 마지막 결제가 아무리 튀어도 "구독료 인상"이 된다.

2026-08-24 실측: 이마트가 4·5·6월에 각 1건(41,000 / 38,000 / 217,000), 간격 31·34일로
조건을 만족해 아래 신호가 나왔다.

```
이마트 결제는 2026-05-19의 38,000원에서 2026-06-22 217,000원으로 179,000원 늘었고,
증가 비율은 4.7105263157894735이며 3회 기준 연간 영향은 2,148,000원입니다.
```

영향도 2,148,000원으로 **1위**에 올라, 진짜 구독료 인상인 넷플릭스(36,000원)를
인사이트 카드 밖으로 밀어낼 수 있다. 한 달에 우연히 세 번 간 마트가 구독으로 보이는
것은 임계값 문제가 아니라 **판정에 "정기성"의 근거가 금액 편차뿐**이라는 문제다.

고칠 방향: `recurring_price_up` 의 인상 비율에 상한을 두거나(예: 100% 초과는 인상이
아니라 이상 결제로 본다), 반복 판정에 결제일 근접성(매월 같은 날 ±3일)을 더한다.
전자가 싸고, 후자가 옳다.
