# xlsx 명세서 업로드 — 브라우저에서 CSV 로 변환

2026-08-31 · 대상 `src/components/UploadDialog.tsx`, 신규 `src/lib/xlsx/`

## 왜 고치나

카드사에서 내려받는 이용대금명세서의 기본 형식이 xlsx 다. 지금은 CSV 만 받으므로 사용자는 엑셀을 열어 "다른 이름으로 저장 → CSV" 를 직접 해야 한다. 업로드가 이 제품의 첫 관문인데, 그 앞에 수동 변환 단계가 하나 서 있다.

**목표.** 카드사에서 받은 xlsx 를 그대로 끌어다 놓으면 업로드가 되게 한다.

## 지키는 선

`CLAUDE.md` 의 CRITICAL 규칙에서 온다.

- **업로드 원본 파일은 Next.js 서버를 통과하지 않는다.** 서명 URL로 클라이언트가 Storage 에 직접 올리고, 읽기는 Inngest 워커만 한다
- **Storage 키의 파일명은 서버가 생성**하고, 클라이언트가 준 이름은 DB 컬럼에만 저장한다
- 순수 로직은 `src/lib/` 에 둔다
- 새 기능은 테스트를 먼저 쓴다 (TDD)

→ 이 설계는 **서버·워커·미리보기 라우트·DB 스키마를 한 줄도 바꾸지 않는다.** 변환은 전부 브라우저에서 끝나고, Storage 에 올라가는 것은 지금과 똑같은 CSV 바이트다.

## 결정 사항

브레인스토밍에서 세 갈래를 골랐다.

| 갈림길 | 선택 | 버린 쪽과 이유 |
|---|---|---|
| 파싱 위치 | **브라우저에서 CSV 로 변환 후 업로드** | 서버/워커 파싱은 원본 xlsx 가 보존되어 재처리에 유리하지만, 서버측 의존성과 압축 해제 폭탄 방어가 따라온다. 브라우저 변환은 서버를 전혀 안 건드린다 |
| 정리 범위 | **헤더 행 탐지 + 빈 행/열 제거까지만** | 합계행·할인행까지 걷어내는 명세서 특화 정리는 "날짜 없는 행은 버린다" 류 휴리스틱이 카드사별로 오작동하고, 할인 금액이 집계에서 사라진다 |
| 라이브러리 | **`read-excel-file` (9.3.10, MIT)** | npm 의 `xlsx` 는 0.18.5 에 멈춰 있고(공식 배포는 자체 CDN 으로 이동) prototype pollution·ReDoS CVE 가 그 버전에 걸려 있다. `exceljs` 는 1MB 급으로 무겁다 |

**트레이드오프를 명시한다.** 브라우저 변환을 고른 대가로 **원본 xlsx 는 어디에도 남지 않는다.** 변환이 잘못됐을 때 사후에 원본을 열어볼 방법이 없고, 재현은 사용자에게 파일을 다시 받아야 한다.

## 데이터 흐름

```
파일 선택
  ├ .csv  → (변경 없음) 파일 그대로 업로드
  └ .xlsx → readSheet()   : File → string[][]        (read-excel-file, dynamic import)
            → sheetToCsv(): string[][] → CSV 문자열   (순수 함수)
            → new Blob([csv], { type: "text/csv" })
  ↓
signed-url 요청  filename = 원본 .xlsx 이름 / contentType = "text/csv" / size = 변환 후 바이트
  ↓
Storage 직접 업로드 → Inngest 워커는 지금 그대로 decodeCsv → parseCsv
```

**순서가 중요하다.** `src/app/api/uploads/signed-url/route.ts:59` 가 클라이언트가 보낸 `size` 를 10MB 상한과 대조하고, 그 값이 서명에 들어간다. 그러므로 **변환을 끝낸 뒤** signed-url 을 요청해야 한다. 지금 코드는 `handleSubmit` 에서 signed-url → 업로드 순이므로, 변환을 그 앞에 넣는다.

`filename` 은 원본 `.xlsx` 이름을 그대로 보낸다. 사용자가 올린 파일이 그것이고, Storage 키는 어차피 서버가 `randomUUID()` 로 만든다(`route.ts:112`).

## 모듈

### `src/lib/xlsx/sheetToCsv.ts` — 순수 함수, 테스트의 본체

```ts
export function sheetToCsv(rows: readonly (readonly unknown[])[]): string
```

세 가지를 한다.

**1. 헤더 행 탐지.** 앞에서 최대 20행을 훑어 **비어있지 않은 셀이 가장 많은 행**을 헤더로 잡는다. 동률이면 가장 위. 그 위의 행은 버린다.

실제 명세서에 대입하면 이렇게 잡힌다.

| 행 | 내용 | 비어있지 않은 셀 | 판정 |
|---|---|---|---|
| 1 | `> 카드이용내역` | 1 | 버림 |
| 2 | `이용일자 / 이용카드 / 구분 / 이용가맹점 / 이용금액 / …` | 9 | **헤더** |
| 3 | `원금 / 수수료` (서브헤더) | 2 | 데이터 행으로 내려감 |
| 4~51 | 거래 46건 | 6 | 데이터 |
| 52~55 | 소계·합계·리볼빙·총금액 | 3 | 데이터 행으로 내려감 |

이 규칙의 실패 모드는 하나다. **데이터 행이 헤더보다 더 많이 채워져 있으면** 데이터 행이 헤더로 잡혀 그 위 거래가 통째로 날아간다. 명세서는 헤더가 가장 넓은 행인 것이 보통이고 동률이면 위쪽을 택하도록 편향을 줬지만, 완전히 막지는 못한다. 이 경우 잘못된 헤더는 컬럼 매핑 단계에서 걸려 사용자에게 수동 매핑을 요구하게 된다 — 조용히 틀린 데이터가 들어가지는 않는다.

**2. 빈 열·빈 행 제거.** 전 행에 걸쳐 값이 하나도 없는 열(명세서의 A열 들여쓰기 열 등)과, 모든 셀이 빈 행을 지운다.

**3. 셀 → 문자열.**

| 셀 타입 | 출력 | 이유 |
|---|---|---|
| `Date` | `YYYY-MM-DD` | `src/lib/csv/date.ts` 가 그대로 받는다 |
| `number` | 지수 표기 없는 십진수 | `1e+21` 같은 문자열이 금액 파서로 가면 안 된다 |
| `null` / `undefined` | 빈 문자열 | |
| 그 외 | `String(value)` | |

CSV 이스케이프는 필수다. **이 파일 2행 마지막 셀이 이미 `적립예정\n포인트` 로 개행을 품고 있어서**, 따옴표로 감싸지 않으면 헤더가 두 줄로 깨진다. `,` · `"` · 개행 중 하나라도 있으면 `"` 로 감싸고 내부 `"` 는 `""` 로 이스케이프한다.

### `src/lib/xlsx/readSheet.ts` — 라이브러리 경계

```ts
export async function readSheet(file: File): Promise<unknown[][]>
```

`read-excel-file` 을 `await import()` 로 지연 로딩해 첫 시트를 읽는다. 사용자가 xlsx 를 고른 순간에만 내려받으므로 평상시 번들에는 들어가지 않는다. 이 파일에는 로직을 두지 않는다 — 테스트는 `sheetToCsv` 를 겨눈다.

### `src/components/UploadDialog.tsx` — 분기

- `isCsvFile()` 을 `isAcceptedFile()` 로 넓혀 `.csv` · `.xlsx` 를 받는다
- `accept` 속성에 `.xlsx` 와 그 MIME 을 추가한다
- `handleSubmit` 에서 xlsx 면 변환을 거쳐 `Blob` 을 만들고, 그 크기로 signed-url 을 요청한다
- 안내 문구를 바꾼다. 현행 "CSV 파일만 올릴 수 있습니다. 카드사에서 '엑셀 저장' 대신 'CSV 저장'을 선택하세요" 는 이제 틀린 안내다

## 에러 처리

| 상황 | 사용자에게 |
|---|---|
| 확장자가 csv·xlsx 가 아님 | "CSV 또는 엑셀(.xlsx) 파일만 올릴 수 있습니다." |
| xlsx 파싱 실패 (손상·암호·xls) | "엑셀 파일을 읽지 못했습니다. 카드사에서 CSV 로 내려받아 올려주세요." |
| 시트가 비었거나 데이터 행 0 | "표를 찾지 못했습니다. 파일을 확인해 주세요." |
| 변환 후 10MB 초과 | 기존 크기 에러 문구를 그대로 탄다 |

합계행·서브헤더가 데이터로 섞여 들어가는 문제는 여기서 처리하지 않는다. 기존 `runSanityCheck`(`src/lib/csv/sanity.ts:56`)가 이상 행 비율로 판정하고, 임계값은 `src/lib/csv/thresholds.ts` 한 곳에 있다.

## 테스트

TDD 로 간다 — 테스트를 먼저 쓰고 통과하는 구현을 쓴다.

**`src/lib/xlsx/sheetToCsv.test.ts`** — 실제 명세서 모양을 `string[][]` fixture 로 만들어 검증한다.

1. 제목행(`> 카드이용내역`) 아래의 9칸 행이 헤더로 선택된다
2. 통째로 빈 A열이 사라진다
3. 개행을 품은 셀(`적립예정\n포인트`)이 따옴표로 감싸여 헤더가 한 줄로 유지된다
4. `Date` 셀이 `YYYY-MM-DD` 로 나온다
5. 큰 수가 지수 표기로 나가지 않는다
6. 헤더 후보가 동률이면 위쪽 행이 선택된다
7. 데이터가 없으면 빈 문자열을 돌려준다

**`src/components/UploadDialog.test.tsx`** — xlsx 를 고르면 `contentType: "text/csv"` 와 **변환 후 크기**로 signed-url 을 요청하는지. `readSheet` 는 모킹한다.

**로컬 end-to-end** — 실제 `이용대금명세서_20260803.xlsx` 를 올려 46건이 들어가는지 확인한다. 여기서 확인할 것은 변환 자체가 아니라 **합계 4행 + 서브헤더 1행 + 할인 2행이 sanity 임계치를 넘지 않는가** 다. 넘으면 임계값 조정이 아니라 정리 범위 결정을 다시 논의한다.
